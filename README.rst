PyCryptodome-static
===================

This is a fork of `PyCryptodome`_ where the native code is **no longer
built as separate ``.pyd`` extension modules with setuptools**.

Instead, all C sources are compiled by **CMake** into a **single static
library** for MSVC (``pycryptodome_static.lib``). The library contains:

* the C code of every native module (hash functions, ciphers, ECC, math),
  exposing the same ``EXPORT_SYM`` C primitives as before, and
* the ``PyInit_*()`` entry point of every former ``.pyd`` module
  (42 in total, generated by the ``FAKE_INIT`` macro in ``src/common.h``)
  — and nothing else.

A host program only needs to link ``pycryptodome_static.lib`` and register
the ``PyInit_*()`` functions; the C primitives can also be called directly.

Building with CMake
-------------------

Requirements:

* CMake 3.20 or newer
* Visual Studio 2019/2022/2026 with MSVC (x64 or x86)
* a CPython installation (only the headers are needed, e.g. for
  ``Python.h`` and ``PyMODINIT_FUNC``)

::

    cmake -S . -B build -DPython3_ROOT_DIR="C:/Program Files/Python314"
    cmake --build build --config Release

The result is ``build/Release/pycryptodome_static.lib``, together with
``build/Release/pycryptodome_link_check.exe``, a sample consumer that
forces every object of the library to be linked (checking that all 42
``PyInit_*()`` entry points resolve and that there are no duplicate
symbols) and runs a small smoke test.

To install the library and the public header into ``CMAKE_INSTALL_PREFIX``::

    cmake --install build --config Release

Using the library
-----------------

Link your program against ``pycryptodome_static`` and include
``src/pycryptodome_init.h``. The header declares every ``PyInit_*()``
function together with the ``PYCRYPTODOME_INIT_TABLE`` X-macro, which
maps each former extension module to its entry point::

    #include <Python.h>
    #include "pycryptodome_init.h"

    /* Example: register all entry points before Py_Initialize() */
    #define REGISTER(name, fn) PyImport_AppendInittab(name, fn);
    PYCRYPTODOME_INIT_TABLE(REGISTER)

The C primitives (e.g. ``MD5_init``, ``AES_start_operation``,
``mont_mult``, ``strxor``) are also available: the sources under ``src/``
act as the public headers (``common.h``, ``errors.h``, ``block_base.h``,
``mont.h``, ...). A minimal CMake consumer looks like this::

    add_executable(my_app main.c)
    target_link_libraries(my_app PRIVATE pycryptodome_static)

or, with an existing Visual Studio project, add the include paths for
``src`` and ``src/libtom``, then link ``pycryptodome_static.lib``.

.. note::

    The ``PyInit_*()`` stubs return ``NULL`` by design: in the original
    PyCryptodome, the ``.pyd`` files are loaded by the Python package
    through ctypes/cffi as plain DLLs, not through the import machinery.
    When merging everything into a static library, the host program is
    responsible for wiring the primitives and the entry points into its
    own environment. The pure-Python frontend is still available under
    ``lib/Crypto`` for reference and for embedding scenarios.

Layout
------

* ``CMakeLists.txt`` — build description of the static library
* ``src/`` — C sources (the former extension modules), plus
  ``pycryptodome_init.h``
* ``lib/Crypto`` — the pure-Python frontend of PyCryptodome
* ``examples/consume_static.c`` — example consumer / link check

Notes on the conversion
-----------------------

* ``mont1.c``, ``mont2.c`` and ``mont3.c`` only existed to work around a
  distutils race condition; ``mont.c`` is now compiled once and shared by
  ``ec_ws.c``, ``curve448.c``, ``ed448.c`` and ``modexp.c``.
* ``sub_mod()`` in ``src/bignum.c`` was made ``STATIC`` because
  ``bignum.c`` is included by several translation units
  (``mont.c``, ``mod25519.c``); each unit keeps a private copy, as it was
  the case with the former per-DLL build.
* The feature macros that ``compiler_opt.py`` used to detect at setup time
  (``SYS_BITS``, ``HAVE_INTRIN_H``, ``USE_SSE2``, ``LTC_NO_ASM``, ...)
  are now set directly in ``CMakeLists.txt``. AES-NI and PCLMUL support
  is always compiled in on MSVC x64.
